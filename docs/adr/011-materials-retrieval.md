# ADR-011: Materials module and retrieval design

Status: Accepted

## Decision

Material ingestion, chunking, embeddings, and retrieval get a **new module, `modules/Materials`**, not an extension of Assessments. The retrieval pipeline is consumed by two independent surfaces — Assessments' AI-drafted quiz generation and a learner-facing AI tutor chat — neither of which is naturally "an Assessment," and Core is not an option because ingested material is an educational concept tied to organizations/subjects (`core/README.md`: "if a concept is specific to... a Subject... it belongs in a module, not Core"). Materials owns `materials`/`material_chunks`, the async chunking+embedding job, and the retrieval service; Assessments gains a new, documented dependency on Materials (alongside its existing Academics/Learners/Staff dependencies) for quiz-draft generation only — it does not gain a hard dependency on Materials' ingestion or chat surfaces.

**Ingestion scope for this pass is text only**, not PDF, despite the brief naming "PDF/text." No PDF-text-extraction library is in `composer.json`, and adding one (e.g. `smalot/pdfparser`) is a real new dependency decision this ADR does not make unilaterally — AGENTS.md requires composer changes be explicit, not incidental to an unrelated feature. `MaterialIngestionService::ingest()` takes already-extracted text; a PDF upload path is a documented follow-up that plugs in ahead of the same chunking job once a library is chosen.

**One embeddings + retrieval pipeline, not two.** `core/AIGateway` gains a narrow `Contracts\EmbeddingProviderInterface` (`embed(string $text): array`) alongside the existing `AIProviderInterface`, and `AIManager::embed()` resolves a provider implementing it — mirroring the existing provider-resolution pattern exactly. Only `GeminiProvider` implements it for now (Google's `models/{model}:embedContent`), since it is the one provider this phase makes real end-to-end; the platform default provider (`ollama`) is not embedding-capable in this codebase, so Materials always requests `config('ai.embedding_provider')` (defaults to `gemini`) explicitly rather than the tenant/platform default.

**Vector storage is a JSON float array column plus brute-force cosine similarity in PHP at query time**, not a dedicated vector database or a MySQL/SQLite vector extension — this stack has neither (MySQL 8.0 predates native `VECTOR`; SQLite has none), and standing up pgvector/Pinecone/etc. for this phase is out of scope. This is a real, working, "actually wired up" design for the material volumes a tutoring/school organization's own uploaded content realistically produces (hundreds to low thousands of chunks per organization, scoped per query to one organization and often one subject) — not a claim it scales to a global corpus. If that ever becomes the bottleneck, the swap is `MaterialRetrievalService`'s single query method, not a second implementation kept alongside this one.

**AI-drafted quiz generation never bypasses the existing review gate.** `QuizDraftService` (Assessments) retrieves relevant chunks, asks Gemini for structured draft questions, and inserts them as ordinary `AssessmentQuestion` rows on a `Draft`-status `Assessment` via the same path a teacher's manually-authored questions use — the assessment still requires an explicit `QuizService::publish()` call before any learner can see or attempt it. No new "AI-published" state is introduced.

**The AI tutor chat is retrieval-scoped to the querying learner's own organization, always.** `TutorChatService` resolves the organization from the authenticated learner's own enrolment/membership context exactly like every other learner-portal surface (`LearnerPortalController`'s pattern) — it never accepts an organization identifier as client input. `MaterialRetrievalService::topK()` always filters chunks by `organization_id` at the query level, not by post-filtering results, so there is no path where a cross-organization chunk is ever loaded into memory for a request, let alone returned. This is tested explicitly (org-isolation test named in the brief), not just asserted here.

## Consequences

Assessments gains one new, documented cross-module dependency (Materials), consistent with its existing Academics/Learners/Staff dependencies; Materials gains none on Assessments — the dependency is one-directional. `core/AIGateway`'s `AIProviderInterface` is unchanged; embeddings are a separate, optional capability a provider may additionally implement, so Ollama/DeepSeek/OpenAI/Claude need no changes and are unaffected. PDF ingestion, a real vector index, and giving other providers embeddings support are named, deliberate gaps, not silent omissions — each is a follow-up ADR/PR, not a hidden TODO.
