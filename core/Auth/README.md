# core/Auth

**Purpose**: platform authentication — login, logout, password reset, email verification, and account-status enforcement. Part of the Sky Fundi Platform Core, per [/core/README.md](../README.md).

**Responsibilities**:
- `Application/AuthService` — shared credential and account-state validation, API login token issuance (`login()`, or `authenticate()` + `issueToken()` separately when a caller must gate on two-factor status first), login/logout auditing, password reset, and bulk token revocation. The web-session controller reuses `authenticate()` and never creates an API token.
- Sanctum-based bearer tokens for the API (see [API Authentication](../../docs/api/authentication.md)); session guard reserved for Blade.
- `Http/Controllers/Api/V1` — Login, Logout, ForgotPassword, ResetPassword, EmailVerification, TwoFactor, TwoFactorChallenge controllers, all thin per [Clean Architecture](../../docs/architecture/clean-architecture.md).
- `Http/Middleware/CheckAccountLocked` — defence-in-depth guard so a token issued before a lock/suspend can't keep working.
- `Listeners/RevokeTokensOnAccountLock` — proactively revokes tokens when `Core\Users` fires `UserLocked`/`UserSuspended`.
- Password reset uses Laravel's built-in password broker (`config/auth.php`); email verification uses the `MustVerifyEmail` contract already on `Core\Users\Infrastructure\Models\User`.
- **Two-factor authentication (TOTP, RFC 6238)** — `Application/Totp` implements the algorithm in plain PHP (no third-party TOTP/QR dependency; verified against the RFC 4226 reference HOTP vectors in `tests/Unit/Auth/TotpTest.php`). `Application/TwoFactorAuthenticationService` owns enrollment/confirmation/verification/disable/recovery-codes — the only place `users.two_factor_*` is read or written, via `forceFill()` rather than `$fillable` so it can never become mass-assignable elsewhere. `Application/TwoFactorEnforcementService` reads a per-organization opt-in setting (`security.enforce_two_factor`, via the existing `Modules\Organizations\Application\OrganizationService` settings mechanism — same pattern as `Modules\Staff\Application\TeachingAssignmentService`'s `enforce_teaching_assignments`). `Application/TwoFactorLoginService` sits between password authentication and login completion: `Domain\Enums\TwoFactorStatus` is `NotRequired` (login completes immediately, unchanged from before), `ChallengeRequired` (user has 2FA enabled; must submit a code or recovery code), or `SetupRequired` (their organization enforces 2FA and they haven't enrolled; must complete enrollment before login completes). The web flow tracks the pending user via the session (never `Auth::login()`s until the second factor clears); the API flow is stateless, so `LoginController` issues a short-lived encrypted challenge token instead of a real Sanctum token, exchanged at `POST /api/v1/auth/two-factor-challenge`.

**Allowed dependencies**: `Core\Users` (the user model and `UserService` for lockout bookkeeping), `Core\AuditLogs` (every auth event is audited), `Modules\Organizations` (`OrganizationService::settings()`, read-only, for two-factor enforcement — the one place this module reads a module's data, mirroring the existing precedent of module settings being read generically). Never a module dependency the other direction.

**Routes**: `POST /api/v1/auth/login`, `POST /api/v1/auth/two-factor-challenge`, `POST /api/v1/auth/logout`, `POST /api/v1/auth/forgot-password`, `POST /api/v1/auth/reset-password`, `POST /api/v1/auth/email/verify/{id}/{hash}`, `POST /api/v1/auth/email/resend`, and self-service `GET|POST /api/v1/auth/two-factor`, `POST /api/v1/auth/two-factor/confirm`, `DELETE /api/v1/auth/two-factor`, `POST /api/v1/auth/two-factor/recovery-codes`.

**Web entry**: `GET /login`, `POST /login`, and CSRF-protected `POST /logout` use Laravel's encrypted server-side session guard. Successful login regenerates the session; logout invalidates it and regenerates the CSRF token. Destination resolution uses platform permissions and active organization memberships. Eligible organization users reach the permission-protected `GET /dashboard`; multiple memberships require trusted server-side selection first. Users without usable organization access receive a factual access page. Two-factor: `GET|POST /two-factor/challenge` (existing 2FA, mid-login, guest-gated), `GET /two-factor/setup` (forced enrollment, guest-gated), `POST /two-factor/enroll` + `GET /two-factor/recovery-codes` (shared between the forced and voluntary paths — see `App\Http\Controllers\TwoFactorController::resolveUser()`), and authenticated self-service under `GET|POST /security/two-factor/*`.

**Known gap, disclosed rather than hidden**: no QR-code image rendering — enrollment shows the manual-entry key and the raw `otpauth://` URI as text (any authenticator app supports manual entry); adding QR rendering would mean either a new dependency or building a QR encoder from scratch, neither done unilaterally here. No organization-admin self-service UI to toggle `enforce_two_factor` — it goes through the existing platform-wide organization-settings endpoint, consistent with `enforce_teaching_assignments` having the same gap.
